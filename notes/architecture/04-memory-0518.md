# Memory System Architecture

nanobot 的记忆系统采用三层架构设计，平衡实时性和深度处理，通过渐进式压缩降低成本。

## 1. 三层记忆架构

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: Session (短期记忆)                                 │
│    ├─ 存储位置: sessions/*.jsonl                             │
│    ├─ 内容: 完整对话历史（未压缩）                             │
│    ├─ 生命周期: 用户清空会话后丢失                             │
│    ├─ 触发机制: token 超限触发 Consolidator                  │
│    └─ 核心: 动态对话管理                                      │
└─────────────────────────────────────────────────────────────┘
                    ↓ (Consolidator 摘要)

┌─────────────────────────────────────────────────────────────┐
│  Layer 2: history.jsonl (中期记忆)                           │
│    ├─ 存储位置: memory/history.jsonl                         │
│    ├─ 内容: LLM 摘要的关键事实                                │
│    ├─ 生命周期: 持久化存储（跨会话）                           │
│    ├─ 触发机制: 定时任务触发 Dream                            │
│    ├─ 游标机制: cursor (自增编号)                             │
│    └─ 核心: 渐进式压缩                                        │
└─────────────────────────────────────────────────────────────┘
                    ↓ (Dream 深度处理)

┌─────────────────────────────────────────────────────────────┐
│  Layer 3: 期记忆文件                                       │
│    ├─ USER.md: 用户身份、偏好、习惯                           │
│    ├─ MEMORY.md: 项目上下文、知识、事件                       │
│    ├─ SOUL.md: Agent 行为、语气设定                           │
│    ├─ skills/: 可复用的工作流技能                             │
│    ├─ 生命周期: 持久化存储 + Git 版本控制                      │
│    ├─ 加载时机: 每次对话加载到 prompt                         │
│    └─ 核心: 知识固化                                          │
└─────────────────────────────────────────────────────────────┘
```

## 2. 核心组件职责

### 2.1 MemoryStore — 数据访问层（DAO）

**定位**：纯文件 I/O 层，无业务逻辑

**代码位置**: `nanobot/agent/memory.py:31-338`

**核心职责**：

| 职责 | 方法 | 说明 |
|------|------|------|
| **文件路径管理** | `__init__` | 统一管理所有记忆文件路径 |
| **读/写操作** | `read_memory()`, `write_memory()` | 纯文件 I/O，异常处理 |
| **JSONL 格式处理** | `append_history()`, `_read_entries()` | 追加写入 + cursor 自增 |
| **游标管理** | `get/set_last_dream_cursor()` | 维护处理进度 |
| **Git 版本控制** | `self.git` | 集成 GitStore，追踪长期记忆文件 |
| **历史压缩** | `compact_history()` | 清理超过 max_history_entries 的旧条目 |
| **数据迁移** | `_maybe_migrate_legacy_history()` | 自动迁移旧版 HISTORY.md |

**设计价值**：

- **分离关注点**：业务逻辑（Consolidator/Dream）与数据访问分离
- **依赖注入**：可测试、可替换、共享实例
- **封装复杂性**：JSONL 格式、游标机制、异常处理全部封装
- **统一接口**：业务类只需调用 `append_history()`，不关心底层细节

**关键代码**：

```python
# 追加写入（核心方法）
def append_history(self, entry: str) -> int:
    cursor = self._next_cursor()                          # 自增 cursor
    ts = datetime.now().strftime("%Y-%m-%d %H:%M")
    record = {"cursor": cursor, "timestamp": ts, "content": entry}

    with open(self.history_file, "a", encoding="utf-8") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")  # JSONL 格式

    self._cursor_file.write_text(str(cursor))
    return cursor

# 读取未处理条目（游标过滤）
def read_unprocessed_history(self, since_cursor: int) -> list[dict]:
    return [e for e in self._read_entries() if e["cursor"] > since_cursor]
```

### 2.2 Consolidator — 压缩器（短期 → 中期）

**定位**：token 压缩触发器，快速摘要

**代码位置**: `nanobot/agent/memory.py:345-550`

**触发时机**：

- **自动触发**：`estimated > budget` 时（每次对话后异步检查）
- **手动触发**：用户输入 `/new` 命令（归档未压缩部分）

**核心流程**：

```
1. 估算当前 prompt tokens (estimate_session_prompt_tokens)
2. 计算 budget = context_window - max_completion - 1024 (安全缓冲)
3. 判断 estimated > budget?
    ├─ No → 直接返回（不压缩）
    └─ Yes → 循环压缩（最多 5 轮）
        ├─ 找用户消息边界 (pick_consolidation_boundary)
        ├─ 截取 chunk (最多 60 条消息)
        ├─ LLM 摘要 (archive)
        ├─ 写入 history.jsonl
        ├─ 更新 session.last_consolidated
        └─ 目标: 压缩到 budget / 2
```

**关键方法**：

```python
async def archive(self, messages: list[dict]) -> str | None:
    """LLM 摘要 + 写入 history.jsonl"""
    formatted = MemoryStore._format_messages(messages)
    response = await self.provider.chat_with_retry(
        messages=[
            {"role": "system", "content": "Extract key facts..."},
            {"role": "user", "content": formatted},
        ]
    )
    summary = response.content or "[no summary]"
    self.store.append_history(summary)  # ⭐ 写入 history.jsonl
    return summary

async def maybe_consolidate_by_tokens(self, session: Session) -> None:
    """token 超限触发压缩"""
    budget = self.context_window_tokens - self.max_completion_tokens - 1024
    target = budget // 2
    estimated = self.estimate_session_prompt_tokens(session)

    if estimated < budget:  # ⭐ 未超限不压缩
        return

    for round_num in range(5):
        if estimated <= target:
            return
        chunk = session.messages[session.last_consolidated:end_idx]
        await self.archive(chunk)  # ⭐ 调用 archive 写入
        session.last_consolidated = end_idx
```

**关键特点**：

- **不是每次对话都写入**：只有 token 超限或 `/new` 时才触发
- **写入内容是摘要**：LLM 提取关键事实，不是完整对话
- **追加式写入**：`open(history_file, "a")` — 不覆盖已有内容
- **游标自增**：每次写入分配新的 cursor 编号

### 2.3 Dream — 深度处理器（中期 → 长期）

**定位**：深度分析和分类整理，固化长期记忆

**代码位置**: `nanobot/agent/memory.py:557-768`

**触发时机**：

- **自动触发**：定时任务（默认每 2 小时）
- **手动触发**：用户输入 `/dream` 命令

**两阶段处理**：

#### Phase 1: 分析（dream_phase1.md）

```
输入: 未处理的 history.jsonl 条目 + 当前文件内容
输出: 标记列表（每行一个）
    ├─ [FILE] 原子事实（如 "has a cat named Luna"）
    ├─ [FILE-REMOVE] 过时内容（>14天的临时信息）
    └─ [SKILL] 可复用的工作流模式

规则:
    ├─ 子化: "has a cat"，不用 "discussed pets"
    ├─ 过时判定: 天气、会议、已完成任务 >14天
    ├─ 技能发现: 重复 2+ 次 + 明确步骤 + 足够重要
    └─ 不添加: 当前天气、临时错误、对话填充
```

#### Phase 2: 执行（dream_phase2.md）

```
输入: Phase 1 分析结果 + 当前文件内容 + 现有技能列表
工具: read_file / edit_file / write_file
执行:
    ├─ edit_file(USER.md): 添加用户偏好
    ├─ edit_file(MEMORY.md): 更新项目知识
    ├─ edit_file(SOUL.md): 调整 Agent 行为（较少）
    ├─ write_file(skills/<name>/SKILL.md): 创建新技能
    └─ 去重检查: 创建技能前检查现有技能

规则:
    ├─ 批量合并: 同一文件的多个修改合并为一个 edit_file 调用
    ├─ 精确编辑: 使用完整 old_text（包含前后空行）
    ├─ 技能质量: <2000 词，包含使用场景、步骤、示例
```

**后处理**：

```python
# nanobot/agent/memory.py:743-767
new_cursor = batch[-1]["cursor"]
self.store.set_last_dream_cursor(new_cursor)  # ⭐ 更新游标（避免重复处理）
self.store.compact_history()                   # ⭐ 清理旧条目

if changelog and self.store.git.is_initialized():
    sha = self.store.git.auto_commit(f"dream: {ts}, {len(changelog)} change(s)")  # ⭐ Git 提交
```

**游标机制**：

```
未处理条目 = cursor > dream_cursor 的 history.jsonl 条目

示例:
    history.jsonl:
        cursor=1 ─┐
        cursor=2 ─┼─ dream_cursor=0 → 处理 1,2 → dream_cursor=2
        cursor=3 ─┤
        cursor=4 ─┼─ dream_cursor=2 → 处理 3,4 → dream_cursor=4
        cursor=5 ─┘

关键:
    ├─ cursor: 每个条目的自增编号（写入时分配）
    ├─ dream_cursor: Dream 上次处理到的位置（处理后更新）
    ├─ 增量处理: 只处理新增的未处理条目
    └─ 避免重复: 即使 Phase 2 失败也推进游标（防止死循环）
```

## 3. 数据流详解

### 3.1 完整数据流转

```
用户对话
    ↓
Session.messages 增长（完整对话）
    ↓ (每次对话后异步检查)
AgentLoop._process_message()
    ↓
AgentLoop._schedule_background(consolidator.maybe_consolidate_by_tokens(session))
    ↓
estimated > budget?
    ├─ No → 直接返回（不写入 history.jsonl）
    └─ Yes → 循环压缩
        ├─ 截取 chunk = session.messages[last_consolidated:end_idx]
        ├─ Consolidator.archive(chunk)
            ├─ LLM 摘要 → provider.chat_with_retry()
            ├─ 写入 history.jsonl → MemoryStore.append_history()
            └─ cursor 自增
        └─ session.last_consolidated = end_idx

定时任务（每 2 小时）或用户输入 /dream
    ↓
Dream.run()
    ├─ 读取未处理条目 → cursor > dream_cursor
    ├─ Phase 1 分析 → LLM 提取标记
    ├─ Phase 2 执行 → AgentRunner + 工具调用
        ├─ edit_file(USER/MEMORY/SOUL.md)
        ├─ write_file(skills/<name>/SKILL.md)
    ├─ 更新 dream_cursor
    ├─ compact_history()
    ├─ Git auto_commit
    └─ 返回 True/False（是否处理了内容）

下次对话
    ↓
ContextBuilder.build_messages()
    ├─ 加载 USER.md → 用户偏好
    ├─ 加载 MEMORY.md → 项目知识
    ├─ 加载 SOUL.md → Agent 行为
    ├─ 加载 skills/ → 技能指令
    └─ 构建完整 system prompt
    ↓
Agent 看到用户偏好和历史知识
```

### 3.2 关键数据结构

**history.jsonl 格式**（JSONL，每行一个 JSON）：

```json
{"cursor": 1, "timestamp": "2025-01-15 14:00", "content": "User prefers concise Chinese replies..."}
{"cursor": 2, "timestamp": "2025-01-16 13:00", "content": "Discussed async patterns..."}
{"cursor": 3, "timestamp": "2025-01-17 10:00", "content": "Repo summarize requested third time..."}
```

**游标文件**：

- `.cursor`: 最新 cursor 编号（每次写入 history.jsonl 时更新）
- `.dream_cursor`: Dream 处理进度（每次 Dream 完成后更新）

## 6. 核心设计理念

### 6.1 分层处理的价值

**为什么需要三层？**

1. **token 效率**：
   - Session: ~10,000 tokens（动态）
   - history.jsonl: ~2,000 tokens（可选加载）
   - USER/MEMORY/SOUL: ~500 tokens（每次加载）

2. **渐进式处理成本**：
   - Consolidator: 高频触发（token 超限），低成本（单次 LLM 摘要）
   - Dream: 低频触发（定时任务），高成本（两次 LLM + 工具调用）

3. **数据持久化**：
   - Session: 用户清空后丢失（但已归档到 history.jsonl）
   - history.jsonl: 持久化存储（跨会话）
   - USER/MEMORY/SOUL: Git 版本控制（可回滚）

### 6.2 游标机制的价值

**为什么需要游标？**

1. **增量处理**：只处理新增的未处理条目（`cursor > dream_cursor`）
2. **避免重复**：已处理的条目不会再次分析
3. **成本可控**：每次 Dream 最多处理 20 条（max_batch_size）
4. **失败容错**：即使 Phase 2 失败也推进游标（防止死循环）

### 6.3 Git 版本控制的价值

**为什么需要 Git？**

1. **版本控制**：每次 Dream 变更自动提交，可回滚（`/dream-restore`）
2. **审计追踪**：可查看长期记忆文件的变更历史
3. **安全保障**：误操作可恢复

## 8. 设计模式应用

### 8.1 MemoryStore 的多重身份

```
MemoryStore 定位:

1. 辅助类 ✅
    ├─ 提供文件读写、游标管理等辅助功能
    ├─ 有静态方法（read_file）
    └─ 被业务类调用

2. 数据访问对象（DAO）⭐⭐⭐
    ├─ 封装数据存储复杂性（JSONL 格式、游标机制）
    ├─ 提供统一访问接口（append_history, read_unprocessed_history）
    ├─ 屏蔽底层细节（文件路径、编码、异常）
    └─ 有状态管理（cursor、dream_cursor）

3. 基础设施服务⭐⭐⭐⭐（最准确）
    ├─ 提供系统级基础能力（文件系统、Git 版本控制）
    ├─ 被多个组件依赖（Consolidator、Dream、ContextBuilder）
    ├─ 持久化服务（游标文件）
    ├─ 生命周期长（贯穿运行周期）
    └─ 需要依赖注入
```

## 9. 典型使用场景

### 9.1 场景 1：日常对话 + 自动 Dream

```
第 1 天 10:00-14:00:
    ├─ 用户对话累积 token = 68,000 > budget
    ├─ Consolidator 自动压缩 → history.jsonl cursor=1
    ├─ .dream_cursor = 0（未处理）

第 1 天 16:00:
    ├─ 定时任务触发 Dream
    ├─ 读取 cursor=1（未处理）
    ├─ Phase 1 分析 → Phase 2 执行
    ├─ 更新 USER.md + MEMORY.md + skills/
    ├─ .dream_cursor = 1（已处理）

第 2 天 09:00-13:00:
    ├─ 新对话累积 token 超限
    ├─ Consolidator → history.jsonl cursor=2
    ├─ .dream_cursor = 1（未处理 cursor=2）

第 2 天 15:00:
    ├─ 定时任务触发 Dream
    ├─ 读取 cursor=2（cursor > dream_cursor=1）
    ├─ 更新 USER.md
    ├─ .dream_cursor = 2（已处理）
```

### 9.2 场景 2：手动触发 Dream

```
用户输入 /dream:
    ├─ 立即返回 "Dreaming..."
    ├─ 后台执行 Dream.run()
    ├─ 处理未处理条目
    ├─ 发送 "Dream completed in 8.3s."

再次输入 /dream:
    ├─ dream_cursor 已更新
    ├─ 无未处理条目
    ├─ 返回 "Dream: nothing to process."
```

### 9.3 场景 3：用户回滚长期记忆

```
用户输入 /dream-log:
    ├─ 显示最新 Dream 的变更
    ├─ Git diff: USER.md, MEMORY.md

用户输入 /dream-restore <sha>:
    ├─ Git revert 到指定版本
    ├─ 恢复长期记忆文件到之前状态
```

## 10. 总结

nanobot 的记忆系统通过三层架构实现了：

1. **渐进式记忆**：Session → history → 长期记忆，分层处理降低成本
2. **个性化体验**：USER.md 让 Agent 记住用户偏好，自动适配
3. **知识累积**：MEMORY.md 记录项目背景，跨会话持久化
4. **角色定制**：SOUL.md 定义 Agent 行为，可调整"个性"
5. **自动化工作流**：skills/ 固化可复用模式，提升效率
6. **数据安全**：Git 版本控制 + 游标机制，可回滚且不丢失

核心组件：
- **MemoryStore**：数据访问层，封装文件 I/O、游标、Git
- **Consolidator**：压缩器，token 超限触发，快速摘要
- **Dream**：深度处理器，定时任务或手动触发，分类整理长期记忆

最终效果：用户感觉 Agent "很懂我"，不必每次都重复说明偏好，Agent 还能自动发现和固化常用工作流。
